> 目标：让项目在大量使用 AI/Codex 辅助开发的情况下，仍然保持**可控、可审查、可回滚、可持续扩展**，避免“改得快但越来越乱”。
<callout icon="⚙️" color="blue_bg">
	**工程原则：小步提交、接口先行、测试跟随、自动门禁、随时可回滚。**
	任何一次开发都必须能回答：改了什么、为什么改、影响哪些模块、如何验证、出问题怎么退。
</callout>
# 一、标准开发闭环
每个功能都走同一套流程：
需求 / Bug
→ Issue
→ 设计影响检查
→ Contract / Schema 变更判断
→ 小分支开发
→ 单元测试
→ 集成测试
→ PR
→ CI
→ 人工 Review
→ 合并 main
→ 构建 Preview
→ Release Candidate
→ 正式 Release
→ 回归与问题记录
**禁止直接在 main 上堆功能。**
---
# 二、Issue 先行
任何超过“小改字/改样式”的工作都先建立 Issue。
## Issue 模板
必须包含：
- **目标**：想解决什么问题。
- **用户价值**：普通用户会得到什么。
- **涉及模块**：Source / Normalizer / Analyzer / Scoring / Storage / UI。
- **是否改 Contract**：是 / 否。
- **是否改数据库 Schema**：是 / 否。
- **是否增加权限**：是 / 否。
- **风险**：可能破坏什么。
- **验收标准**：什么情况下算完成。
- **测试计划**：需要哪些 fixture / unit / E2E。
- **回滚方式**：出现问题后如何关闭或恢复。
### Issue 标签建议
- type:feature
- type:bug
- type:refactor
- type:test
- type:docs
- area:source
- area:analyzer
- area:scoring
- area:storage
- area:ui
- risk:low
- risk:medium
- risk:high
---
# 三、分支策略
推荐保持简单：
- main：始终可发布。
- feat/xxx：新功能。
- fix/xxx：Bug 修复。
- refactor/xxx：结构调整。
- test/xxx：测试改进。
- docs/xxx：文档。
示例：
- feat/favorite-source
- feat/trend-scoring
- fix/spa-user-switch
- refactor/evidence-store
## 规则
- 一个分支只解决一个主题。
- 尽量在 1–2 天内完成。
- 单个 PR 不要同时改 Source、Scoring、UI 三大层，除非功能确实跨层且拆不开。
- 大功能拆成多个可单独合并的小 PR。
---
# 四、Contract First 工作流
只要涉及跨模块数据，就先检查 Contract。
## 开发前先问四个问题
1. 是否新增字段？
2. 是否修改字段语义？
3. 是否改变可空性？
4. 是否改变版本兼容性？
如果答案为“是”，先改：
- TypeScript interface；
- Zod schema；
- fixture；
- contract test；
- migration（如需要）。
然后再写业务实现。
## 破坏性变更
不能直接改旧接口。
例如：
- Analyzer API v1 保持兼容；
- 新需求做 Analyzer API v2；
- 给旧实现留迁移周期；
- 明确 deprecated 字段。
---
# 五、AI / Codex 辅助开发流程
AI 可以大量写代码，但不能拥有“随便改整个仓库”的自由度。
## 每次给 AI 的任务应包含
1. **只改哪些目录**。
2. **禁止改哪些核心接口**。
3. **目标行为**。
4. **现有测试必须继续通过**。
5. **需要新增什么测试**。
6. **不要顺手重构无关代码**。
7. **输出变更摘要和风险**。
推荐提示约束：
> 只完成当前 Issue。不要扩大范围。优先复用现有 Contract 和工具函数。任何跨模块接口变更必须单独指出。先读相关测试，再实现；完成后运行 typecheck、unit、integration，并解释失败项。
## AI 生成代码后的人工检查
至少检查：
- 是否绕过现有抽象层；
- 是否出现重复实现；
- 是否硬编码 B 站原始字段到 Core；
- 是否引入隐藏网络请求；
- 是否扩大浏览器权限；
- 是否吞掉错误；
- 是否增加无测试分支；
- 是否偷偷改变评分规则；
- 是否造成缓存不兼容。
### AI 禁止事项
- 未经明确 Issue 就大规模重构。
- 自动升级全部依赖后顺便修代码。
- 删除“看起来没用”的兼容层。
- 直接修改稳定 Topic ID。
- 为通过测试而删除测试。
- 用 try/catch 静默吞错。
- 新增服务器依赖。
---
# 六、PR 质量门禁
每个 PR 必须回答：
## PR 描述
- **What**：做了什么。
- **Why**：为什么需要。
- **Scope**：改了哪些模块。
- **Risk**：风险点。
- **Tests**：跑了哪些测试。
- **Screenshots**：UI 改动时必须提供。
- **Migration**：是否涉及本地数据库。
- **Permissions**：是否新增浏览器权限。
- **Rollback**：如何关闭/撤回。
## 自动 CI 门禁
至少：
1. pnpm install --frozen-lockfile
2. lint
3. prettier check
4. typecheck
5. unit test
6. integration test
7. fixture golden test
8. build Chrome
9. build Edge/Chromium
10. bundle size check
### 高风险 PR 额外要求
以下任一情况自动标记 high risk：
- 改 SourceAdapter Contract；
- 改 Evidence schema；
- 改 scoring 核心公式；
- 改数据库 schema；
- 改扩展权限；
- 引入新模型；
- 引入新网络域名。
高风险 PR 必须增加：
- migration / compatibility test；
- 回归 fixture；
- 手工验证说明。
---
# 七、测试金字塔
## 1. Contract Test
保证模块接口不被无意破坏。
必须覆盖：
- EvidenceItem；
- SourceResult；
- AnalyzerResult；
- InterestProfile；
- storage schema。
## 2. Unit Test
大量、快速。
重点：
- normalization；
- dedupe；
- scoring；
- decay；
- confidence；
- topic mapping；
- migrations。
## 3. Fixture / Golden Test
这是本项目最重要的测试之一。
保留一批匿名化固定公开样本：
Raw data
→ Pipeline
→ Expected Profile
当算法改动导致结果变化时，CI 明确显示 diff。
**不能随手 update snapshot。**
必须判断结果变化是不是更合理。
## 4. Integration Test
验证模块串联：
Source Fixture
→ Normalize
→ Analyzer
→ Scoring
→ Profile
## 5. E2E
只覆盖高价值路径：
- 打开主页；
- 识别 UID；
- 开始分析；
- 部分 Source 失败；
- 出结果；
- 查看依据；
- SPA 切用户；
- 刷新分析；
- 清理数据。
---
# 八、Definition of Done
一个功能只有满足以下条件才算完成：
- [ ] Issue 验收标准全部完成。
- [ ] 没有绕过既有架构。
- [ ] 新逻辑有测试。
- [ ] 旧测试全部通过。
- [ ] 部分失败有降级。
- [ ] 错误信息用户可理解。
- [ ] 新字段有 schema。
- [ ] 数据结构变更有 migration。
- [ ] 性能没有明显退化。
- [ ] 权限没有无意义扩大。
- [ ] README / 文档需要时已更新。
- [ ] PR 已说明风险和回滚。
- [ ] main 合并后仍然可构建发布。
---
# 九、版本与发布流程
推荐语义化版本：
- patch：0.3.1 → Bug 修复。
- minor：0.4.0 → 新能力，兼容旧数据。
- major：1.0.0 → 稳定公开接口；以后破坏性变化才升 major。
开发阶段：
- v0.1.x
- v0.2.x
- v0.3.x
- v0.5.x
- v1.0.0
## Release 流程
main
→ 自动构建
→ RC 包
→ 本地手工回归
→ 小范围测试
→ 标记 Git tag
→ GitHub Release
→ 扩展商店
→ 观察 Issue / 崩溃反馈
### 发布前 Checklist
- [ ] CI 全绿。
- [ ] manifest 权限 diff 已检查。
- [ ] bundle size 未异常增长。
- [ ] 数据库 migration 测试通过。
- [ ] Chrome / Edge 真实安装测试。
- [ ] 核心用户流程 E2E 通过。
- [ ] CHANGELOG 写完。
- [ ] 已准备回滚版本。
---
# 十、回滚与 Feature Flag
每个实验性功能都尽量能够被单独关闭。
Feature Flag 示例：
- source.favorites.v2
- analyzer.longTail
- semantic.webgpu
- scoring.crossSourceBoost
- ui.shareCardV2
如果某个模块线上有问题：
- 关闭功能；
- 不影响 Core；
- 下一 patch 修复；
- 避免紧急重写整个扩展。
## Release 保留策略
至少保留：
- 当前稳定版；
- 上一个稳定版构建；
- 对应 source map；
- manifest；
- lockfile；
- migration 版本。
---
# 十一、故障定位设计
由于项目默认不上传用户数据，诊断也要“本地优先”。
## 本地诊断报告
扩展提供「复制诊断信息」：
只包含：
- App version；
- browser version；
- manifest version；
- Source 成功/失败状态；
- ErrorCode；
- Analyzer 状态；
- schemaVersion；
- SemanticProvider 状态；
- 耗时统计。
默认**不包含**：
- 用户 UID；
- 评论正文；
- 收藏内容；
- 具体兴趣画像；
- Cookie；
- Token。
用户可以把诊断文本贴到 GitHub Issue。
## ErrorCode 体系
例如：
- SRC_TIMEOUT
- SRC_RATE_LIMITED
- SRC_SCHEMA_MISMATCH
- SRC_PERMISSION_DENIED
- STORAGE_MIGRATION_FAILED
- ANALYZER_TIMEOUT
- ANALYZER_INVALID_OUTPUT
- SEMANTIC_UNAVAILABLE
- PROFILE_PARTIAL
这样 Bug 报告不再只有“不能用了”。
---
# 十二、性能门禁
从开发初期就建立预算。
建议监控：
- 扩展初始 bundle 大小；
- 首屏加载时间；
- 一次分析的证据数；
- 峰值内存；
- IndexedDB 大小；
- 单 Analyzer 耗时；
- SemanticProvider 初始化耗时；
- 整体分析 P50 / P95。
## 原则
- UI 线程不做大批量计算；
- 大计算使用 Web Worker；
- 文本分批；
- embedding 批处理；
- 证据量设置上限；
- 长列表虚拟化；
- 模型 lazy load。
如果某个 PR 让包体、内存或分析时间异常增加，必须解释。
---
# 十三、依赖管理
依赖越少越稳定。
## 新增依赖前必须回答
1. 标准库/现有依赖能不能做？
2. 包是否长期维护？
3. 包体增加多少？
4. 是否会引入网络行为？
5. 是否浏览器兼容？
6. License 是否适合开源项目？
## 自动升级策略
- patch：可自动 PR，但仍跑全套 CI。
- minor：人工 Review。
- major：单独 Issue，禁止和功能 PR 混在一起。
不要一次升级十几个核心依赖然后同时开发功能。
---
# 十四、架构决策记录 ADR
所有重要架构决策建立 ADR。
例如：
- ADR-001：为什么选择 WXT。
- ADR-002：为什么 EvidenceItem 隔离原始数据。
- ADR-003：为什么基础功能不依赖 AI。
- ADR-004：为什么强度与置信度分离。
- ADR-005：为什么不用服务器。
- ADR-006：为什么 Analyzer 不能直接请求网络。
每个 ADR 只需要：
- Context；
- Decision；
- Alternatives；
- Consequences。
这样半年后不会出现“谁知道当初为什么这么设计”。
---
# 十五、重构策略
重构不能和功能开发混在一个大 PR。
推荐：
功能需求
→ 发现结构问题
→ 先记 Tech Debt Issue
→ 当前功能最小改动完成
→ 单独 refactor PR
→ 有测试保护后再改结构
## 什么时候值得重构
满足任一：
- 同类逻辑出现第三次复制；
- 一个文件超过合理职责；
- 一个模块同时知道 UI + 网络 + 算法；
- 测试必须大量 mock 内部实现才能写；
- 新增一个功能需要改 5 个无关模块；
- 常出现循环依赖。
---
# 十六、每个版本后的复盘
每发布一个 minor 版本做一次短复盘：
### 保留
哪些设计证明有效？
### 问题
哪里最容易出 Bug？
### 数据
- Issue 数量；
- Source 失败率；
- 最常见 ErrorCode；
- 回归 Bug；
- 平均分析耗时；
- bundle 增长。
### 决定
下一版本：
- 保留什么；
- 删除什么；
- 重构什么；
- 暂缓什么。
---
# 十七、推荐的日常开发顺序
每次开发都按照：
1. 读 Issue。
2. 找相关 Contract。
3. 读现有测试。
4. 写/补失败测试。
5. 做最小实现。
6. 跑单元测试。
7. 跑相关集成测试。
8. 检查架构边界。
9. 让 AI 做一次独立 Review。
10. 人工看 diff。
11. 提 PR。
12. CI 全绿。
13. 合并。
14. Preview 手测。
这比“让 AI 一次把整个版本写完”慢一点点，但长期会快很多。

# 十九、最终工程目标
最终不是追求“代码永远不出 Bug”，而是做到：
> **Bug 出现在一个明确模块里，能被测试发现，能快速定位，能局部关闭，能安全修复，且不会把整个产品拖垮。**
对于这个项目，理想状态是：
- B站改收藏接口 → Favorites Adapter 红灯；
- 其他 Source 继续工作；
- CI fixture 暴露 schema mismatch；
- 用户看到“收藏数据暂不可用”；
- 基础画像继续生成；
- 修复 Adapter 后发 patch；
- Core / Analyzer / UI 都不用重写。
这才是“稳定性和扩展性好”的工程流程。
