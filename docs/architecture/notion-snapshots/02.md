## 总体目标
把「B站兴趣画像」做成一个 **本地优先、零配置、模块化、可降级、可测试** 的浏览器扩展。
核心原则：
> **采集层可以坏、某个 Analyzer 可以坏、轻量模型可以不可用，但扩展主体不能跟着一起坏。**
<callout icon="🧱" color="blue_bg">
	**架构优先级：稳定性 \> 可解释性 \> 扩展性 \> 算法复杂度。**
	先建立稳定数据管线，再逐步增强兴趣识别。不要在 v0.1 就把复杂 AI、聚类和图谱全部塞进去。
</callout>
## 一、先冻结 6 个核心边界
整体数据流：
Bilibili 页面 → Source Adapter → Normalizer → Evidence Store → Analyzer → Scoring Engine → Interest Profile → UI / Share Card
### 1. Source Adapter：数据源适配器
职责只有一个：把某一种公开数据取回来。
例如：
- 投稿 Adapter
- 动态 Adapter
- 公开收藏 Adapter
- 评论 Adapter
- 用户主页 Adapter
任何 B 站页面结构、接口字段、分页方式变化，都限制在 Adapter 内部解决。
禁止：
- Adapter 自己计算兴趣分数；
- Adapter 直接操作 UI；
- UI 直接请求 B 站数据。
### 2. Normalizer：标准化层
把各种来源统一成 EvidenceItem。
建议字段：
- id
- source
- userId
- timestamp
- text
- title
- tags
- category
- creator
- sourceUrl
- quality
后续所有分析器只接受 EvidenceItem，绝不能依赖 B 站原始 JSON。
### 3. Evidence Store：证据仓库
负责：
- 本地保存证据；
- 去重；
- 缓存；
- 数据版本迁移；
- 清理过期数据。
推荐 IndexedDB 保存证据与画像缓存，`browser.storage.local` 保存设置与少量状态。
每份持久化数据必须包含：
- schemaVersion
- collectedAt
- sourceVersion
- TTL
并从第一版开始保留 migration 机制。
### 4. Analyzer：分析器
Analyzer 不负责采集，只接受标准化 Evidence。
统一输出 InterestSignal，包含：
- analyzerId
- topicId
- topicName
- parentTopicId
- relevance
- confidence
- evidenceIds
- reasons
- timestamp
未来可以有：
- BaseTopicAnalyzer
- EntityAnalyzer
- GameAnalyzer
- ACGAnalyzer
- TechnologyAnalyzer
- MusicAnalyzer
- LongTailDiscoveryAnalyzer
任何 Analyzer 都必须能单独启用、关闭、升级和失败。
### 5. Scoring Engine：统一评分
Analyzer 只产出信号，不自己定义最终 0–100 分。
最终得分统一考虑：
- 行为权重；
- 主题相关度；
- 时间衰减；
- 证据质量；
- 多源一致性；
- 重复行为抑制。
### 6. Profile Model：最终画像
UI 只读取统一 InterestProfile，包括：
- userId
- generatedAt
- topics
- trends
- confidence
- sampleSummary
- warnings
这样 UI 完全不知道采集和算法细节。

## 二、推荐技术栈
### 浏览器扩展
- **TypeScript**：核心语言。
- **WXT**：扩展构建、入口和多浏览器输出。
- **Manifest V3**：Chrome / Edge 主线。
- **React**：结果面板、设置页和分享 UI。
- **Zod**：运行时数据校验。
- **IndexedDB + Dexie**：证据与画像缓存。
- **Vitest**：单元测试。
- **Playwright**：端到端浏览器测试。
### 本地轻量语义能力
不要作为第一阶段硬依赖。
到 v0.3 再引入 ONNX Runtime Web，并把执行后端封装为 SemanticProvider：
- RuleProvider
- MetadataProvider
- WasmEmbeddingProvider
- WebGpuEmbeddingProvider
上层只依赖统一接口，未来换模型不影响其他模块。

# 四、详细制作流程

目标：正式写产品之前，先验证最危险的部分。
### 任务
- [ ] 第一版只支持 Chrome / Edge Chromium。
- [ ] v0.1 只选 2–3 个最稳定且公开的数据源。
- [ ] 准备一组不同类型的公开测试样本。
- [ ] 验证分页、未登录、已登录、隐私关闭、空数据。
- [ ] 验证 SPA 页面切换后 UID 是否正确更新。
- [ ] 验证扩展权限可以最小化。
- [ ] 确认基础版完全不依赖服务端与 API Key。
- [ ] 写清公开数据范围与敏感属性边界。
### 通过标准
至少两个数据源能够稳定获取并成功标准化，才进入 Phase 1。

## Phase 2 — Contract First
目标：先写接口协议，不写复杂算法。
### 必须定义
- [ ] EvidenceItem
- [ ] RawSourceResult
- [ ] SourceAdapter
- [ ] InterestSignal
- [ ] Analyzer
- [ ] InterestNode
- [ ] InterestProfile
- [ ] AnalysisContext
- [ ] AppError / AppWarning
- [ ] Result 类型
- [ ] Zod schema
核心原则：正常失败不要依赖异常抛出控制流程。
所有模块统一返回：
- 成功 + data + warnings；
- 或失败 + error + recoverable。
---
## Phase 3 — 数据采集层 v1
目标：建立“不怕某个 B 站来源单独变化”的采集系统。
每个 Source Adapter 固定流程：
fetch → schema validation → normalize → deduplicate → quality scoring → EvidenceItem
### 必做稳定机制
- [ ] 单请求 timeout。
- [ ] Source 总 timeout。
- [ ] AbortController，可取消。
- [ ] 仅对可恢复网络错误做指数退避重试。
- [ ] 并发限制。
- [ ] 请求节流。
- [ ] 分页上限。
- [ ] 整次分析数据量上限。
- [ ] 去重。
- [ ] 缓存。
- [ ] schema 校验。
- [ ] 429 / 403 / 未授权等状态分别处理。
- [ ] 各 Source 独立状态。
### 降级原则
例如：
- 投稿成功 ✅
- 动态成功 ✅
- 收藏不可见 ⚠️
- 评论超时 ⚠️
仍然生成画像，但降低置信度并告知数据缺失。
---
## Phase 4 — Normalizer 与 Evidence Store
目标：彻底隔离 B 站原始结构和兴趣算法。
### 任务
- [ ] 每个 Source 最终只输出 EvidenceItem。
- [ ] 统一时间格式。
- [ ] 文本清洗。
- [ ] HTML / URL / 特殊字符处理。
- [ ] 完全重复数据去重。
- [ ] 同一内容跨来源保留关系。
- [ ] 生成稳定 evidenceId。
- [ ] IndexedDB 存储。
- [ ] Profile 缓存。
- [ ] TTL。
- [ ] schemaVersion。
- [ ] migration 测试。
- [ ] 一键删除本地分析数据。
### 强制规则
**Raw 数据不得穿透到 Analyzer/Core/UI。**
Analyzer 的测试必须可以在完全断网状态下只使用 fixtures 运行。
---
## Phase 5 — 基础兴趣分析 v0.1
目标：先做到“基本靠谱”，而不是“什么都能识别”。
### 第一阶段信息优先级
1. B站原有分区；
2. 视频标签；
3. 标题实体；
4. UP 主 / 作品实体；
5. 关键词词典；
6. 重复出现频率。
### Taxonomy
不要只存“原神 = 0.8”。
要建立稳定层级：
娱乐 → 游戏 → 二次元游戏 → 原神
每个 Topic 使用稳定 ID。例如：
- game
- game.gacha
- game.gacha.genshin
显示名称可以改，内部 ID 不随意改。
---
## Phase 6 — Scoring / Confidence / Trend
目标：回答“为什么是这个分数”。
### 行为权重
先做可配置参数，不追求第一版数学完美。
示意：
- 投稿：1.00
- 收藏：0.80
- 动态：0.75
- 长评论：0.70
- 普通评论：0.55
- 弹幕：0.25
实际值以后通过人工样本迭代。
### 时间衰减
时间模型必须独立成模块。
近期行为权重更高，但长期稳定兴趣要有保底，不能因为一年没互动就完全归零。
### 重复抑制
连续几十条同一视频弹幕，不能当几十份独立证据。
需要：
- 同主题时间窗口去重；
- 同视频重复互动降权；
- 同内容转发/重复文本降权。
### 多源增强
同一兴趣同时出现在投稿、收藏、动态，比只在一个来源重复出现更可信。
### 强度和置信度必须分开
**兴趣强度**：这个兴趣对该账号的重要程度。
**置信度**：系统对这个判断有多确定。
禁止混为同一个百分比。
---
## Phase 7 — UI v0.1
目标：小白无需学习。
主界面只保留三个核心动作：
1. 分析兴趣；
2. 查看依据；
3. 重新分析。
### 首屏只显示
- Top 5 一级兴趣；
- 每项 2–5 个子兴趣；
- 强度；
- 置信度；
- 样本数量；
- 数据缺失提示。
### 「为什么」面板
展示：
- 使用了哪些来源；
- 相关证据数量；
- 时间跨度；
- 代表性公开内容；
- 为什么置信度高/低。
普通界面不要显示模型 logits、embedding 和技术日志。

- [ ] 接口异常。
- [ ] 重复分页。
- [ ] 中英混合标题。
- [ ] Emoji / 特殊字符。
### Unit Test
重点测试：
- normalize
- dedupe
- score
- decay
- confidence
- taxonomy
- migration
### Integration Test

- [ ] 校验 hash。
- [ ] Lazy Load。
- [ ] 需要时再初始化。
- [ ] 支持取消。
- [ ] 内存压力时释放。
- [ ] 初始化失败自动 fallback。

# 五、稳定性设计
## 1. 单点故障隔离
任意一个 Source / Analyzer 都不能阻断整个 Pipeline。
多个独立模块采用 settled 聚合思路，而不是一个失败全部失败。
## 2. 分层超时
分别设置：
- 单请求 timeout；
- 单 Source timeout；
- 单 Analyzer timeout；
- 整次 Analysis timeout。
## 3. 缓存优先
同一个 UID 短时间重复分析：
- 优先显示上次画像；
- 用户主动刷新时重新采集；
- 避免重复打请求。
## 4. Feature Flag
新数据源、新 Analyzer、新模型都通过本地 Feature Flag 控制。
发现线上问题时可以快速默认关闭单一模块，而不动 Core。
## 5. Schema Validation
所有外部输入都视为不可信。
HTTP 200 不代表字段结构一定正确。
## 6. 数据迁移
IndexedDB 每次破坏性结构变化都必须有 migration。
禁止把“让用户手动清缓存”当升级方案。
## 7. 性能预算
- UI 首屏不等待语义模型；
- 文本分批处理；
- 重计算放 Worker；
- 长列表虚拟化；
- 限制最大证据量；
- 语义推理批处理。
## 8. 内存预算
不要长期保存全部 embedding 和中间向量。
长期保存必要证据、特征摘要和最终画像即可。

# 六、可扩展性设计
稳定扩展点只保留四个：
1. **SourceAdapter** — 新数据来源。
2. **Analyzer** — 新领域分析。
3. **SemanticProvider** — 新本地语义引擎。
4. **Renderer** — 新画像 / 分享展示。
其他地方不要做万能插件系统。
> 扩展点越多不代表越高级。少而明确的稳定扩展点更容易长期维护。

# 九、最终验收标准
## 功能
- [ ] 普通用户安装后直接使用。
- [ ] 打开用户主页即可分析。
- [ ] 输出一级和二级兴趣。
- [ ] 核心兴趣均可查看依据。
- [ ] 数据不足时明确说明。
- [ ] 能显示时间变化。
- [ ] 能处理部分数据不可访问。
## 稳定性
- [ ] 一个 Source 崩溃不会导致整次分析崩溃。
- [ ] 一个 Analyzer 崩溃不会导致 UI 崩溃。
- [ ] 模型不可用仍能生成基础结果。
- [ ] 外部字段异常被 schema 层拦截。
- [ ] 数据库升级不要求用户手动清缓存。
- [ ] SPA 页面切换稳定。
- [ ] 所有长任务可取消。
## 可扩展性
- [ ] 新增 Source 不修改 Scoring/UI。
- [ ] 新增 Analyzer 不修改采集层。
- [ ] 换语义模型不修改 Analyzer API。
- [ ] 新增分享样式不修改 Profile 数据结构。
- [ ] API Version 可以管理破坏性变化。
## 用户体验
- [ ] 无服务器部署。
- [ ] 无注册。
- [ ] 无 API Key。
- [ ] 无本地 AI 配置。
- [ ] 错误信息普通用户能看懂。
- [ ] 结论可解释，不只是数字。

# 十、三条不可破坏的工程纪律
1. **任何 B 站字段都不能直接穿透到 Core。**
2. **任何可选能力失败后都必须存在降级路径。**
3. **任何画像结论都必须能够追溯到 Evidence。**
只要这三条一直守住，以后增加数据源、兴趣领域、本地模型或者浏览器平台时，项目就不容易演变成难维护的“大泥球”。
